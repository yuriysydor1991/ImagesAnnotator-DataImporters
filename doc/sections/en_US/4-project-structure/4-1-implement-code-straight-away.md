## Where the importers implementation lives

A call chain through the library is short. A consumer fills the `LibraryContext` descendant of the wanted layout, hands it to `ILib::perform_import()` and gets the annotations of the directory it named through `LibraryContext::set_import_path()` merged into the database it named through `LibraryContext::set_db()`:

- [src/lib/facade/LibraryFacade.cpp](/src/lib/facade/LibraryFacade.cpp) - the installed facade. Every static method simply asks `iadi0impl::LibFactory` for the requested object, so that no implementation type appears in a public header.
- [src/lib/facade/LibraryContext.cpp](/src/lib/facade/LibraryContext.cpp) - the accessors of the installed `LibraryContext`, whose data members are private. It is named by the `IADI_FACADE_SRC` list of [src/CMakeLists.txt](/src/CMakeLists.txt), so every test executable driving a context compiles it the way the library target does.
- [src/lib/libmain/LibMain.cpp](/src/lib/libmain/LibMain.cpp) - the only `ILib` implementation. `LibMain::perform_import()` creates the importer of the given context, publishes it back through `ctx->set_importer()` and calls `IImporter::import_db()` with that very same context.
- [src/lib/libmain/LibFactory.cpp](/src/lib/libmain/LibFactory.cpp) - the factory. `LibFactory::create_importer()` maps the type of the given context onto a concrete importer with one `std::dynamic_pointer_cast` per layout, and returns a `nullptr` for a context naming no known layout.
- [src/lib/facade/public](/src/lib/facade/public) - the `LibraryContext` descendants: `PlainTxtImportLibraryContext`, `Yolo4ImportLibraryContext` and `PyTorchImportLibraryContext`. Each is an installed header only class which inherits the whole of `LibraryContext` - the type itself is what names the layout, so no importer has to appear in the public interface. None of them adds anything at all, since everything an import needs is held by the base class.
- [src/importers](/src/importers) - one sub-directory per dataset layout, each a sub-component of its own with its sources, its `CMakeLists.txt` and its unit tests: [PlainTxt](/src/importers/PlainTxt) holds `PlainTxtFolder2DBImporter`, [Yolo4](/src/importers/Yolo4) holds `Yolo4Folder2DBImporter` and [PyTorch](/src/importers/PyTorch) holds `PyTorchVisionFolder2DBImporter`. All of them stay in the `iannotator::importers` namespace. Two files remain at the component root, since every one of them shares both: `ImportersAliases.h` pulls the installable interface names and the data drivers record names into that namespace, so the importers refer to them unqualified, and `Folder2DBImporter` carries the half of an import which is the same for every layout - the guards over the context, the resolving of the image measuring instance, the merge into the database and the count reported back. What tells the importers apart is the one `read_dataset()` method that base asks them for.
- [src/sizers](/src/sizers) - `ImageSizeFactory` answers at the run time whether this build ships an image size reader of its own, and `OpenCVImageSizer` is that reader, compiled only into a build which found OpenCV.
- [src/helpers](/src/helpers) - `IHelper` and `TypeHelper`, the latter shortening the numeric conversions the coordinate maths needs. Both are header only.

The helper namespace is nested under `iannotator::importers` on purpose. The data drivers library carries top level namespaces of the same names, and both libraries end up in the same process.

### Adding a new import format

1. Implement `Folder2DBImporter::read_dataset()` in a new class under a new sub-directory of [src/importers](/src/importers), named after the layout the way `PlainTxt`, `Yolo4` and `PyTorch` are. Derive from `Folder2DBImporter`, include `ImportersAliases.h`, keep the class in the `iannotator::importers` namespace and do not mark it with `IADI_API` - the importers stay private to the shared object and are reached through `IImporter` only. Override `needs_image_sizer()` to return `true` when the layout can not be read at all without measuring its images, the way the YOLO v4 and the PyTorch Vision ones do.
1. Declare a new `LibraryContext` descendant in [src/lib/facade/public](/src/lib/facade/public), copying one of the existing headers. It stays empty unless the layout asks for data no other one needs, in which case it carries the accessors of that data, and its source goes into the `IADI_FACADE_SRC` list. Mark it `IADI_API` - the cast below needs its typeinfo to leave the shared object.
1. Add a `std::dynamic_pointer_cast` for it to `iadi0impl::LibFactory::create_importer()` in [src/lib/libmain/LibFactory.cpp](/src/lib/libmain/LibFactory.cpp), returning the new importer.
1. Give the layout a factory method of its own - a `create_<layout>_library_context()` on `iadi0impl::LibFactory` and the `LibraryFacade` one-liner forwarding to it - the way every other layout has one, so a consumer never has to name the descendant itself. The mocked `LibFactory` of [src/lib/facade/tests/mocks](/src/lib/facade/tests/mocks) carries a `MOCK_METHOD` per factory method, so it gains one too.
1. Give the new sub-directory a `CMakeLists.txt` with the `target_sources()` call of its own sources and an `add_subdirectory(tests)`, then `add_subdirectory()` it from [src/importers/CMakeLists.txt](/src/importers/CMakeLists.txt). Declare its source list in [src/CMakeLists.txt](/src/CMakeLists.txt) next to `IADI_PLAIN_TXT_SRC`, `IADI_YOLO4_SRC` and `IADI_PYTORCH_SRC` - each of them starting with the shared `IADI_IMPORTERS_COMMON_SRC` - and append it to the `IADI_IMPORTERS_SRC` union. Those lists are what the test executables compile from.
1. Add a `tests/unit/<YourImporter>` tree inside the new sub-directory, the way each layout carries its own. Copying the whole `tests` directory of one of the existing sub-components is the quickest start - see [Project tests](/doc/sections/en_US/4-project-structure/4-4-project-tests.md).

The library decodes no image format of its own. Anything that needs pixels - the measuring the normalised layouts can not be read without - is delegated to the `IImageSizeFacility` implementation supplied by the consumer, or to the OpenCV one a build which found it ships.
